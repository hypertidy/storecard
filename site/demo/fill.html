Which cells are missing?

A store can name the value that means "no data here" in four places: the Zarr array's fill_value, the CF attributes _FillValue and missing_value, and the STAC catalog's nodata. A reader usually looks in one. When it looks in the wrong one, or finds the right number and compares it the wrong way, land and ice are drawn as data, at the bottom of the colour ramp. This page reads three published stores under four reader rules. The card reads every source, casts each to the stored type, and checks that they agree.

Each count is cells masked, out of the fill cells found without any of the four rules: for the F01 stores, the NaN cells of their float32 twin f01e; for f08b, the cells whose value is beyond ±1e19, which no ocean temperature is. The card's mask equals that set, cell for cell, in all three stores; the page says so in red at the top if it ever does not.

Why -1e20 misses

The ocean model writes its fill as float32. The nearest float32 to -1e20 is -100000002004087734272, and that is the value in every land cell. The Zarr fill_value carries it exactly (-1.0000000200408773e+20). The STAC nodata says -1e20, which float32 cannot hold. A browser reads the cell into a 64-bit number and compares: -1.0000000200408773e+20 === -1e20 is false, in every cell. NumPy 2 compares np.float32(-1e20) == -1e20 as true, because it casts the Python number down to float32 first; the same check written in float64 is false. The reader's language decides whether land is masked. The card casts every source to the stored type before comparing, and reports the STAC value as FILL_NOT_REPRESENTABLE.

The CF _FillValue on the same store is the string "AAAAgB2vFcQ=": xarray writes floating-point fill attributes for Zarr v3 as the base64 of their eight bytes. xarray reads it back; a reader expecting a number gets NaN from it and masks nothing.
